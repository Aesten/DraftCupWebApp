# Draft Cup — Specification

## What is Draft Cup?

Draft Cup is a web platform for running competitive team draft tournaments for Mount & Blade II: Bannerlord multiplayer. The core concept is an **auction-based team formation system**: tournament organizers run live auctions in which team captains bid against each other to acquire players for their roster. This creates balanced, community-driven teams with an element of strategy around budgeting, player valuation, and class composition.

The platform covers the full lifecycle of a tournament: player pool setup, auction configuration, live bidding sessions, group-stage match tracking, bracket management, and a finals pick-ban process for map and faction selection.

---

## Tech Stack

**Backend**: Bun runtime, Hono web framework, SQLite via `bun:sqlite`, JWT-based authentication via HTTP-only cookies.

**Frontend**: React 19, Vite 7, TypeScript (strict, erasable syntax only), React Router v7, Tailwind CSS v4, Lucide icons. Fonts (loaded from Google Fonts in `index.html`): Cinzel (display: names, headings, labels, buttons), Alegreya (body), JetBrains Mono (numbers, codes, commands).

**Theme — "Iron & Gilt"**: dark only. Defined once in `client/src/index.css` by remapping Tailwind's stock palette names to the theme, so every `zinc-*`, `amber-*`, `red-*`, `green-*` class string in the codebase is re-themed without editing it: zinc → warm iron greys and parchment text, amber → gilt (used as thin metal: winning bid, primary action), red → blood (live, danger, cavalry), green/emerald → forest (complete), blue → steel (host), violet → plum (auctioneer). Radii are 2–4px, borders are hairlines, no glow, blur or pulsing. Primitives live in `client/src/components/ui/`: `Panel`/`PanelHead`/`Label`, `Button`/`buttonCls`, `Seal` (status stamp), `Field`/`Input`, `Modal`, `Rule`/`Heading`. New UI must use these rather than ad-hoc class strings. Role checks in components go through `hooks/usePermissions.ts`. Row types and API payloads are shared with the server from `shared/types.ts` (`@shared/types`).

## Roles & Authentication

Four distinct roles, each with different access scopes:

**Admin** — Single superuser authenticated by an environment variable password (`ADMIN_PASSWORD`). No database row. Issues a short-lived JWT on login. Can manage everything: create/delete host accounts, set featured tournaments, manage tokens, override scores, reset brackets, manage the global map pool.

**Host** — Tournament organizer. Authenticated by a short token (`DRAFT-XXXXXX`) generated by the admin and stored on the tournament row (`host_token`). The host JWT is scoped to that single tournament; a host who runs several tournaments logs in with each one's token. Revoking the token invalidates future logins. There is no `hosts` table.

**Auctioneer** — Volunteer who runs the live bidding screen. Authenticated by a short token (`DRAFT-XXXXXX`) generated per-tournament and stored on the tournament row. One token covers all auctions in a tournament since divisions run sequentially. Multiple auctioneers can share the token.

**Captain** — Team captain participating in an auction. Authenticated by a per-captain token generated by the host. Scoped to a single auction. Can bid, rename their team, and participate in the pick-ban session if they reach the finals.

Authentication is cookie-based (HTTP-only, `SameSite=Lax`, 14-day expiry). The middleware (`src/middleware/auth.ts`) validates JWTs on every request and attaches the decoded payload to the request context via Hono's typed environment. `requireAuth(...roles)` decides which roles may call a route; `src/services/access.ts` decides whether this caller may act on this row (`canAccessTournament`, `canManageTournament`, `canAccessAuction`, `canAccessSession`). Every route that touches a tournament-owned row uses both.

## Backend Architecture

```text
src/index.ts            Hono app, static files, WebSocket upgrade
src/routes/*.ts         HTTP layer: authenticate → check access → parse body → call service → broadcast
src/services/
  access.ts             who may touch what
  auctionSession.ts     the live-auction state machine (all session/queue/bid/purchase transitions)
  bidRules.ts           pure bidding rules (money in integer thousandths, floor, budget, cooldown)
src/db/
  schema.ts             CREATE TABLE statements (baseline)
  migrations.ts         versioned migrations on PRAGMA user_version; append, never edit
  database.ts           bun:sqlite connection + query helpers
src/ws/rooms.ts         broadcast-only rooms: "state changed, re-fetch"
src/**/*.test.ts        bun test (rules unit tests + route integration tests)
```

Rules of the house: routes contain no game logic; services contain no HTTP; every mutating service call is one synchronous SQLite transaction; the client never enforces a rule the server does not also enforce.

Commands: `bun run test`, `bun run typecheck`, `bun run dev:server`, `bun run build`.

## Database Schema (migration v1)

The schema version lives in `PRAGMA user_version` and is advanced by `src/db/migrations.ts` at start-up. Migration 1 is the baseline below; schema changes are appended as new migrations.

### `tournaments`
Top-level tournament container, e.g. "Draft Cup XV". Belongs to a host. Fields: `id`, `name`, `slug` (unique, URL-safe, auto-generated from name), `description`, `host_token`, `auctioneer_token` (shared across all auctions), `map_pool` (JSON array of map IDs for rolling), `finals_map_pool` (JSON array of map IDs for pick-ban), `players_per_team` (default 6, excluding the captain), `status` (active/archived), `is_featured` (at most one tournament is featured globally), `created_at`.

### `players`
The player pool for a tournament, shared across all auctions within it. Fields: `id`, `tournament_id`, `name`, `classes` (comma-separated string: `inf`, `arc`, `cav` — a player can have multiple), `is_available` (set to 0 when purchased), `created_at`.

### `auctions`
One per division within a tournament (e.g. "Division A", "Division B"). Fields: `id`, `tournament_id`, `name`, `min_increment` (default 0.1), `bid_cooldown_seconds` (pause after each bid before closing, default 3), `is_public`, `status` (setup → ready → finished), `created_at`.

There is **no default budget** at the auction level — every captain has an individually configured budget, set manually by the host to allow skill-based handicapping.

### `captains`
One row per team captain slot per auction. Expected to be exactly 8 per auction. Fields: `id`, `auction_id`, `display_name`, `team_name` (set by captain after login), `token` (login code), `budget`, `class` (optional: inf/arc/cav — the captain's own class).

### `auction_sessions`
A live run of an auction. Fields: `id`, `auction_id`, `status` (pending → live → paused → finished), `sold_count`, `skipped_count`, `half_budget` (1/0, toggle controlling whether the 50%-budget cap is enforced), `created_at`, `started_at`, `finished_at`.

### `session_queue`
Ordered list of players up for auction within a session. Fields: `id`, `session_id`, `player_id` (nullable), `player_name` (snapshot), `queue_position`, `status` (pending → active → sold). Unique on `(session_id, queue_position)`.

### `session_purchases`
Record of every successful sale. Fields: `id`, `session_id`, `captain_id`, `player_id`, `player_name` (snapshot), `price`, `purchased_at`.

### `session_bids`
All bids placed during a session. The most-recent row per `queue_entry_id` is the current top bid. Fields: `id`, `session_id`, `queue_entry_id`, `captain_id`, `captain_name`, `amount`, `placed_at`.

### `session_chat`
Free-text chat messages within a session. Fields: `id`, `session_id`, `author_role`, `author_name`, `content`, `sent_at`.

### `factions`
Global static table, seeded once at DB init. The 6 Bannerlord factions: Vlandia, Battania, Sturgia, Aserai, Khuzait, Empire.

### `maps`
Global map pool, managed exclusively by the admin (not per-tournament). Fields: `id`, `name`, `tags`, `game_id` (in-game identifier used in server commands, e.g. `mp_skirmish_valley`; optional, falls back to name if null), `image_path` (uploaded image), `is_active`. Tournaments reference maps by ID in their `map_pool` and `finals_map_pool` JSON columns.

### `matchups`
One rolled result per match. Captures which map is played and which faction each side uses. Fields: `id`, `tournament_id`, `bracket_id` (null for shared/non-bracket matchups), `round`, `label` (e.g. "A:1v2", "SF1", "Final"), `map_id`, `faction_a_id`, `faction_b_id`, `is_public` (0 = draft; 1 = visible to all), `created_at`.

Matchups are rolled one at a time by the host. The roller picks a random available map (excluding already-used or manually excluded maps in the current round) and assigns two random factions.

### `brackets`
One per auction. Represents the tournament bracket for a division. Fields: `id`, `tournament_id`, `auction_id`, `name`, `slots` (JSON array: captain assignments to the 8 slots), `locked` (0 = host can shuffle; 1 = locked, only admin can reset), `is_public`, `created_at`.

### `matches`
Individual matches within a bracket. Generated when the bracket is first generated. Fields: `id`, `bracket_id`, `round` (1–3 = group stage, 4 = semi-finals, 5 = finals), `match_order`, `match_label`, `group_label` ('A', 'B', or null for knockouts), `captain_a_id`, `captain_b_id`, `matchup_id`, `score_a`, `score_b`, `winner_captain_id`, `status` (pending/played), `is_finals` (1 = triggers pick-ban creation when both finalists are known).

### `pick_ban_sessions`
One per finals match. Created by the host once both finalists are determined. Fields: `id`, `bracket_id`, `match_id` (unique), `status` (waiting → banning → picking → complete), `captain_a_id`, `captain_b_id`, `map_pool` (JSON array of 5 map IDs selected by host), `ban_sequence` (JSON, default `["a","b","b","a"]`), `ban_turn`, `bans` (JSON array of completed bans), `a_joined`/`b_joined`, `chosen_map_id` (the surviving map after all bans), `a_pick`/`b_pick` (faction IDs, hidden until revealed), `revealed`, `created_at`, `completed_at`.

### Sessions (`/api/sessions`)

Every route loads the session, checks `canAccessSession`, and calls `src/services/auctionSession.ts`. "Controllers" are admin and auctioneer.

- `GET /auction/:auctionId` — List sessions for an auction
- `POST /auction/:auctionId` — Create a pending session (shuffled queue from the available pool)
- `GET /:id` — Full session state: active player, upcoming, purchases, captain budgets, bids, `cooldownRemainingMs`, chat
- `GET /:id/purchases`, `GET /:id/pending-players` (alphabetical, hides queue order)
- `POST /:id/sync-pool` — Rebuild the pending queue (pending sessions only)
- `POST /:id/live` / `POST /:id/pause` — Go live (from pending or paused) / pause. Hosts may pause.
- `POST /:id/start` — Activate the first queued player
- `POST /:id/set-active` — Bring a chosen pending player up; the current one is parked at the front with bids wiped
- `POST /:id/bid` — Captain bid, or auctioneer override bid with `captain_id`
- `DELETE /:id/bids/:bidId` — Revoke a bid (admin/host/auctioneer)
- `POST /:id/advance` — `{ action: "sold", expected_bid_id? }` sells to the top bid; `{ action: "sold", captain_id, price }` is a manual sale; `{ action: "skipped" }` sends the player to the back with bids wiped
- `POST /:id/assign` — Hand a pending player straight to a captain at a price
- `POST /:id/refund` — Undo a purchase; that player becomes active again
- `POST /:id/half-budget` — Toggle the half-budget cap
- `POST /:id/finish` — Finish; refused until every roster is full
- `POST /:id/chat` — Post a chat message

#### Bidding rules (server-enforced)

The server is the only authority on bids and sales; the client mirrors these rules for UX only. All rules live in `src/services/bidRules.ts` and are covered by `bun test`.

- Amounts are compared as integer thousandths, never as floats. A bid must be a finite non-negative number with at most 3 decimals and must sit on the `min_increment` grid.
- A captain bid must be at least `top + min_increment` (or `min_increment` with no bids) and at most the captain's remaining effective budget (half-budget mode floors `budget / 2` to one decimal).
- An **auctioneer override bid** (entered on a captain's behalf, `is_override = 1`) only has to be a non-negative multiple of `min_increment`: no budget check, and no floor against the current top — it may match it, or set the price *below* it. A captain could not do either, which is the point — the auctioneer has final say and can hand a player to someone at whatever price is appropriate, even lower than the standing bid. An override skips the pre-sale cooldown.
- Read, validate and insert happen inside one synchronous SQLite transaction, so concurrent bids cannot interleave: the second of two equal bids is always refused.
- The current top bid is the highest amount bid *since the last override on this player* (an override resets the floor instead of being compared against bids that came before it — otherwise a lower override could never win against an earlier, higher captain bid). Within that window, ties favor the earlier bid (lower id); see `TOP_BID_SQL` in `auctionSession.ts`. `placed_at` is written by the server as ISO 8601 with milliseconds. Never order by `placed_at` alone: legacy rows have second resolution.
- A sale (`POST /:id/advance` with `action: "sold"`) re-reads the active player and the top bid inside the transaction, refuses if `expected_bid_id` differs from the current top, refuses while the top bid's cooldown (`bid_cooldown_seconds`) is still running (an override has no cooldown), and refuses if the buyer's remaining budget no longer covers the price.
- Skipping a player deletes his bids; they never resurface when he comes back into the queue.
- `GET /:id` returns `cooldownRemainingMs` so clients count down from server time.
- WebSocket rooms (`src/ws/rooms.ts`) are broadcast-only. They accept no commands and carry no state; every mutation goes through HTTP.

## Tournament Format

Every tournament uses a fixed 8-team format:

**Group Stage** — 8 teams split into Group A (teams 1–4) and Group B (teams 5–8). Each group plays a round-robin over 3 rounds: 2 matches per group per round, 6 matches per group, 12 total group-stage matches.

**Semi-Finals** — 1st of Group A vs 2nd of Group B, and 2nd of Group A vs 1st of Group B. Two matches.

**Finals** — The two semi-final winners face each other. This match triggers the pick-ban session.

**Bracket generation** — The host provides an ordered list of captain IDs. The system assigns them to group slots, generates all round-robin match pairings, and creates semi-final and final placeholder rows.

**Matchup rolling** — For each match the host rolls one matchup (map + two factions) via the roller UI. Maps already used in published matchups in the current round are automatically excluded. The host can additionally exclude specific maps manually. A published matchup cannot be re-rolled.

---

## Pick-Ban Process (Finals Only)

The host creates a pick-ban session for the finals match once both finalists are known. The host selects 5 maps from the tournament's `finals_map_pool` for that session.

**Ban phase** — Both captains log in to `/pickban/:sessionId`. The ban sequence is A → B → B → A (4 bans total), leaving exactly one map. Each captain confirms their identity by joining the session; banning begins once both have joined.

**Pick phase** — Each captain secretly picks a faction from the 6 available. Picks are hidden until both captains have submitted.

**Reveal** — Once both picks are in, the results are revealed simultaneously. The system generates the finals matchup row with the surviving map and the two chosen factions.

**Command** — The result is displayed as a `!setmap` server command: `!setmap <game_id|name> <faction_a> <faction_b>`, with faction names lowercased. The `game_id` field on the map is used if set; otherwise the map name is used as fallback. A copy-to-clipboard button is provided.

## Map Management

Maps are managed globally by the admin via the Maps page (`/admin/maps`). They are not per-tournament.

Each map has:
- **name** — Display name
- **game_id** — In-game identifier used in server commands (e.g. `mp_skirmish_valley`). Falls back to `name` if not set.
- **image** — Uploaded image shown as background in matchup cards
- **tags** — Optional tags for organization

Each tournament has a `map_pool` (JSON array of map IDs used for rolling group-stage / semi-final matchups) and a `finals_map_pool` (JSON array of map IDs available for the host to pick the pick-ban map pool from). These are configured in the tournament's Config tab.

### Shared `TournamentDetail` Component

Core of the host/admin/auctioneer/captain experience (`client/src/components/tournament/TournamentDetail.tsx`). Takes a `slug` and optional `roleOverride`. Renders a tabbed interface:

**Tab: Player Pool** — Searchable, filterable player table. Inline editing and bulk import (JSON/CSV). Class filter pills (Inf/Arc/Cav). Non-managers (auctioneers, captains) see the table read-only.

**Tab: Matchups** — Round selector, map grid (already-used maps auto-excluded or crossed out), rolling animation, result display. List of all rolled matchups below with publish controls.

**Tab: Config** — Auctioneer token management, map pool editor (select which global maps to include), finals map pool editor, tournament description.

**Auction Tabs** (one per auction) — Captain slots table (name, budget, token), bracket creation and management, bracket shuffle/generate.

Only the active tab is mounted. Switching back to a tab is instant because its data is still in the query cache (see below).

### Data layer (`client/src/queries/`)

All server reads go through [TanStack Query](https://tanstack.com/query) hooks; no page keeps a private copy of server data in `useState`, and nothing is threaded through callbacks to keep siblings in sync.

- `keys.ts` — one key factory (`qk`). Keys are hierarchical so one invalidation covers a subtree: `qk.tournament(slug)` covers the row plus its players, matchups, auctions and brackets; `qk.auction(id)` covers the auction row, captains, results and sessions; `qk.pickBanAll()` covers every pick-ban query.
- One module per domain (`tournaments`, `maps`, `players`, `auctions`, `brackets`, `live`) exporting `queryOptions` builders plus `useX` hooks. The builders are reusable with `useQueries` (the admin stats page fans out over every tournament with them).
- `useInvalidate()` returns `invalidate(...keys)`: mutations call the API, then `await invalidate(...)` so the busy flag clears once the refetched data is on screen. When an endpoint returns the updated row (tournament config, pick-ban override, bulk import), the component writes it into the cache with `setQueryData` instead of refetching.
- `live.ts` — `useSessionDetail(id)` and `usePickBanDetail(id)` wrap a query with `useWs`: every server push, and every reconnect, invalidates the query. Because a newer invalidation cancels the in-flight fetch, the most recent server state always wins.
- Defaults (`lib/queryClient.ts`): 30 s stale time, refetch on window focus, no retry on 4xx. Logging out clears the cache; signing in as another role invalidates everything.

## Division Statistics

Each division (auction) can have a stats file uploaded by the host or admin. Stats are stored as JSON in `uploads/stats/{auctionId}.json`. A display config is stored separately in `uploads/stats/{auctionId}.config.json` so it can be updated without re-uploading the data.

### Data upload
Files can be uploaded as `.csv` (semicolon-separated, auto-converted) or `.json`. The CSV parser maps header names to snake_case keys via a fixed column map. Stats are served publicly once uploaded.

### Stats columns
A fixed set of columns is defined in `STAT_COLS` (mirrored in both `StatsTable.tsx` and the export script). The table includes standard combat stats plus two computed columns inserted after S/R: **Cost** (auction purchase price, 1 decimal) and **C/kS** (cost × 1000 / score — a value-for-money metric, excluded for players purchased at ≤ 0.1).

### Display config (`StatsConfig`)
Stored per division, contains:
- `hiddenColumns: string[]` — columns completely hidden from the public table
- `conditions: Record<string, { dependsOn: string; minValue: number }>` — if a dependency column is below the threshold, the cell shows `—` instead of a value (e.g. Hit% requires Shots ≥ 50)
- `gradients: Record<string, GradientType>` — per-column background gradient: `green-up`, `red-up`, `yellow-up` (0 = transparent, max = full color), or `heatmap` (min = red, max = green)
- `nameMap: Record<string, string>` — maps in-game stat names to auction player names; enables Cost/C/kS columns and shows auction names in the table
- `captains: string[]` — in-game names of captains (who don't appear in the auction list); shown with a ♛ crown icon

### Name display
In-game names often include leading clan tags like `[TAG1] [TAG2] PlayerName`. These are stripped for display using a regex (`/^(\[[^\]]*\]\s*)*/`). The auction name (from `nameMap`) takes priority over the in-game name when set.

### Config modal tabs
- **Visibility** — toggle columns on/off for public view
- **Conditions** — add/edit/remove N/A threshold rules
- **Colors** — assign gradient type per column with live color preview
- **Mapping** — link each in-game name to an auction player; captain toggle per row; already-mapped players are excluded from other rows' dropdowns; searchable picker for 60+ player lists

An **Import** bar at the top of the modal allows copying visibility/conditions/colors from another division (nameMap and captains are not imported).

### Public table features
Viewers can sort by any column, filter by name (matches stripped name or auction name), and toggle column visibility locally. Admin-hidden columns are excluded entirely and do not appear in the toggle list.

## Key Design Decisions

**No polling** — Server data lives in one client-side query cache (see "Data layer"). A screen reads it through hooks, shows the cached copy at once, and refetches in the background when it is older than 30 s or the window regains focus. Real-time updates use WebSocket exclusively: the public auction viewer (`AuctionSessionPage`) and the pick-ban session (`PickBanPage`, `PickBanModal`) connect to `/ws/auction/:id` and `/ws/pickban/:id`. The backend broadcasts a lightweight update message after any state change, and the client answers by invalidating the matching query, which refetches the full state.

**Single featured tournament** — The admin sets exactly one tournament as featured. Setting a new one automatically unfeatures the previous.

**Auctioneer token is per-tournament** — One token covers all auctions in a tournament. Since divisions run sequentially, the same auctioneer (or group sharing the token) operates all sessions.

**Captain budgets are always manual** — No default budget. Every captain's budget is set individually by the host to allow skill handicapping.

**Half-budget rule is a session toggle** — The restriction that a captain cannot spend more than half their budget on a single player is toggled per session (`half_budget` flag on `auction_sessions`), not hardcoded.

**Players have a `classes` field, not a hierarchy** — A player can play infantry, archer, cavalry, or any combination. Stored as comma-separated `inf`/`arc`/`cav`. No primary class.

**Brackets are fixed 8-team format** — 2 groups of 4, round-robin, semis, finals. Hardcoded structure. The only variable is which captain occupies which slot.

**Pick-ban is finals-only** — Group stage and semi-final maps are assigned by the matchup roller. Only the finals match gets the interactive pick-ban session.

**Scores are entered manually** — Hosts and admins enter match scores directly in the bracket UI. No screenshot upload or automated verification.

**Maps are global, admin-managed** — The map pool is not per-tournament. The admin maintains a single global list. Each tournament references a subset of those maps via its `map_pool` and `finals_map_pool` ID arrays.

**`game_id` for server commands** — Each map has an optional `game_id` field storing the in-game identifier (e.g. `mp_skirmish_valley`). This value is used in `!setmap` commands. Falls back to the map's display name if not set.

**Stats stored as flat files, not in the database** — Division stats and their display configs are stored as JSON files on disk (`uploads/stats/`), not in SQLite. This keeps the schema stable and makes it easy to re-upload data without a migration. The config is a separate file so it can be updated independently of the data file.

**Mutations invalidate, they do not patch local state** — After a write, a component asks the cache to refetch the keys it touched rather than editing a local array. Every other mounted component reading the same key (the other division tab, the public page in another window after a focus, the admin sidebar) picks the change up for free, and the server stays the single source of truth for derived fields such as budgets and statuses.
