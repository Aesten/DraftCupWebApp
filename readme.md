# BDC Web App

A tournament management platform for Bannerlord Draft Cups. Handles the full lifecycle: player auctions, team drafting, match scheduling, pick-bans, and public-facing stats.

For a detailed breakdown of the data model, API routes, and component architecture, see [spec.md](spec.md).

---

## Roles

### Admin

Logs in at `/admin-login`. Responsible for platform-wide configuration.

- **Hosts**: Create and manage host accounts (username/password). Hosts use these credentials to log in and manage their tournaments.
- **Maps**: Maintain the global map pool used across all tournaments.
- **Featured tournament**: Mark one tournament as "featured" — it appears prominently on the home page.
- **Division stats**: Upload `.csv` or `.json` stat files per division. After uploading, configure column visibility, conditional highlights, color gradients, and player name mappings via the settings (gear) icon. Mark captains with the crown toggle. Import settings from another division to reuse the same column config quickly.
- **Player overrides**: Adjust individual player prices or other auction values after the fact.

---

### Host

Logs in at `/login`. Manages one or more tournaments end-to-end.

**Typical workflow:**

1. **Create a tournament** — set a name and description.
2. **Create divisions** — each division runs its own auction (e.g. "Division 1", "Division 2").
3. **Add players to each division's auction** — paste in player names and set their starting prices.
4. **Assign an auctioneer** — generate a token for the auctioneer to use during the live session.
5. **Run the auction** — the auctioneer runs the live bidding; captains join with their own tokens.
6. **Review teams** — after the auction, view resulting rosters per division.
7. **Set up the schedule** — create matchups for group stage rounds.
8. **Configure pick-bans** — for each matchup (and especially finals), set up the pick-ban map pool.
9. **Mark results** — record match scores and winners.
10. **Manage the bracket** — advance teams through playoff rounds.

Hosts can also set team names and edit rosters directly from the tournament admin panel.

---

### Auctioneer

Accesses the live auction at `/auction/:token` using a token generated by the host.

- Sees the full player pool and current bids.
- Controls auction pacing: start bidding on a player, accept a bid, move to the next player.
- The live session is visible to captains in real time.

---

### Captain

Accesses their team view at `/captain/:token` using a token generated by the host.

- Participates in live bidding during the auction phase.
- After the auction: views their roster, sets or updates the team name.
- During pick-ban phase: interacts with the pick-ban interface to select maps or sides (depending on the configured sequence).

## Public Pages

No login required.

| Route | Description |
|---|---|
| `/` | Home page — shows the featured tournament and general info |
| `/tournaments` | List of all tournaments |
| `/tournaments/:slug` | Tournament detail page — divisions, standings, schedule, stats |

## Development

```bash
./init.sh            # install dependencies and build the frontend
bun run seed:dev     # fill an empty database with a sample tournament (-- --force to replace existing data)
bun run dev:server   # API + WebSocket on :3000
bun run dev:client   # Vite on :5173 (proxies /api to :3000)
bun run test         # server tests
```

The sample data is "BDC XVI": Division 1 finished with a played bracket, Division 2 live in the middle of its auction. The seed prints the login codes (host `DRAFT-HOST01`, auctioneer `DRAFT-AUCT01`, captains `DRAFT-CAPT01` to `DRAFT-CAPT08`). It refuses to run on a database that already contains a tournament unless you pass `--force`.

## Deployment

Production runs on `aesten@3550h` from `~/web/bdc-webapp` as `bdc-webapp.service` (bun on the `PORT` from `.env`, behind nginx for `bdc.aesten.net`). The database (`data/draftcup.db`) and `uploads/` live only on the server.

To deploy, commit to `master`, push, then run from a dev machine:

```bash
git push origin master
scripts/deploy.sh            # add --force to deploy during a live auction/pick-ban
```

[scripts/server-deploy.sh](scripts/server-deploy.sh) then runs on the server:

1. Refuses if the server checkout has local changes, the commit isn't a fast-forward, or an auction (`live`/`paused`) or pick-ban (`banning`/`picking`) is in progress.
2. Backs up the database to `data-backup/deploy-<utc time>-<previous commit>.db` (online `VACUUM INTO`, integrity-checked; the newest 20 are kept).
3. Fast-forwards to the commit, installs with frozen lockfiles and builds the client into `dist/client.next`.
4. Runs the new migrations against the fresh backup copy, so a broken migration fails before the live database is touched.
5. Swaps the build in, restarts the service and waits for `/api/health`.

If any step after the backup fails, the code, dependencies and build are rolled back to the previous commit (and the service restarted if it already was). The database is not restored automatically, because that would discard anything written since the restart; the backup path is printed instead.

**Schema changes** go in [src/db/migrations.ts](src/db/migrations.ts): append a migration with the next version number, never edit an old one. The server applies pending migrations on start-up, each in its own transaction, and records the version in `PRAGMA user_version`.

**One-time server setup** (needs your sudo password, run on the server):

```bash
# let the deploy script restart the service without a password
echo 'aesten ALL=(root) NOPASSWD: /usr/bin/systemctl restart bdc-webapp.service' \
  | sudo tee /etc/sudoers.d/bdc-webapp-deploy && sudo chmod 440 /etc/sudoers.d/bdc-webapp-deploy \
  && sudo visudo -cf /etc/sudoers.d/bdc-webapp-deploy
# start the service on boot
sudo systemctl enable bdc-webapp.service
```

To restore a backup: `sudo systemctl stop bdc-webapp.service`, copy the backup over `data/draftcup.db` (deleting `draftcup.db-wal`/`-shm`), then start the service.

See [spec.md](spec.md) for the full technical specification including API routes, database schema, and component descriptions.
